# Taste — General Preferences

- Prefiere comunicarse en español. Confidence: 0.95
- Propone soluciones concretas de diseño en vez de delegar la decisión al asistente (ej: sugirió el enfoque exacto del honeypot doble checkbox). Confidence: 0.85
- Prefiere honeypots creativos y juguetones sobre CAPTCHAs genéricos — ej: checkbox visible "Los gatos son geniales" + checkbox oculto como trampa para bots. Confidence: 0.9
- Prefiere que el honeypot use un checkbox oculto (no un campo de texto) para atrapar bots que marcan todo. Confidence: 0.85
- Prefiere copy en español y con tono informal/juguetón para elementos de la UI (ej: "Los gatos son geniales" como verificación anti-bot). Confidence: 0.85
- Quiere consistencia de dark mode en todos los elementos nativos del navegador (selects, dropdowns) — no tolera que un control se renderice en claro cuando el tema es oscuro. Confidence: 0.9
- Prefiere soluciones framework-native (ej: API routes de Waku) sobre dependencias de plataforma (ej: Netlify Functions) — quiere que el dev local funcione sin servicios externos. Confidence: 0.9
- Cuando algo no funciona, dirige al asistente a revisar proyectos existentes suyos como referencia en vez de buscar documentación genérica — ej: "Revise [otro proyecto] para ver cómo se maneja ahí el uso de endpoints" y aplicar esas correcciones en el proyecto actual. Confidence: 0.92
- Investiga y corrige por su cuenta antes de pedir ayuda, y al reportar un error incluye el stack trace completo y el contexto de lo que ya intentó (ej: renombró la carpeta a `_api` siguiendo la convención de Waku antes de reportar el error de ruta duplicada). Confidence: 0.7
- Prefiere consolidar la configuración de variables de entorno en un único `.env` y que los scripts de deploy las carguen desde ese archivo (en vez de repartirlas entre `.env` y `.env.local`). Confidence: 0.65
- Mantiene archivos de plan en `planes/` (markdown por proyecto) como checklist vivo de progreso, y los referencia para verificar estado — ej: "¿completado entonces planes\01-ai-code-reviewer.md?". Confidence: 0.8
- Cuando un plan se desvía de la implementación, prefiere documentar las desviaciones en el propio archivo del plan (en vez de dejar el plan obsoleto o cambiar la implementación para coincidir). Confidence: 0.75
- Antes de mergear features nuevas a `main`, pide auditorías de seguridad explícitas mencionando categorías de amenaza concretas (ej: "revise... que no tenga problemas de seguridad, en particular prompt injection y XSS") en vez de pedir un code review genérico. Confidence: 0.9
- Para auditorías de seguridad espera reportes estructurados con formato fijo: Resumen Ejecutivo → Vulnerabilidades por severidad → Lo que está bien hecho → Pruebas faltantes → Plan de remediación priorizado en tabla, con archivo:línea y código de prueba reproducible para cada hallazgo. Confidence: 0.85
- Acepta el framework OWASP LLM Top 10 (LLM01 Prompt Injection, LLM02 Insecure Output, LLM05 Excessive Agency, LLM06 Sensitive Disclosure) como referencia canónica para auditar features con LLMs. Confidence: 0.85
- En auditorías de seguridad prefiere "diagnóstico honesto" — el asistente debe listar explícitamente lo que está bien implementado además de las fallas, sin inflar ni minimizar. Confidence: 0.8
- Para features con LLMs que renderizan output del modelo vía `dangerouslySetInnerHTML` (ej: shiki + CodeBlock), exige defensa en profundidad: sanitización con DOMPurify u otra capa adicional al escape de la librería de highlighting, no fiar la XSS-prevention a una sola dependencia. Confidence: 0.9
- En handlers server-side que manejan API keys de LLM providers, espera `import 'server-only'` explícito para garantizar que el módulo nunca termine en el bundle del cliente, más allá de la convención de ubicación en `src/lib/server/`. Confidence: 0.85
- Prefiere checks de `NODE_ENV` con comparación explícita (`=== 'development'`) sobre la negación (`!== 'production'`), porque el segundo hace fail-open cuando la variable no está seteada. Confidence: 0.8
- Después de aplicar fixes de una auditoría, pide una re-auditoría explícita ("haga de nuevo la auditoria") para verificar que los fixes resuelven los hallazgos previos y no introducen regresiones, en vez de aceptar la auto-reporte del asistente de que todo está arreglado. Confidence: 0.85
- En re-auditorías prefiere una tabla explícita "Hallazgo previo → Estado → Verificado en" al inicio del reporte que mapee cada item de la auditoría anterior a su estado actual (Resuelto/Parcial/No aplicado), para validar de un vistazo el progreso antes de entrar en nuevos hallazgos. Confidence: 0.85
- Cuando agrega copy de transparencia/seguridad visible para visitantes, define la audiencia objetivo explícitamente (ej: "audiencia: recruters") y prefiere un nivel de detalle suficiente para que el usuario entienda qué se registra, sin enumerar exhaustivamente cada campo técnico. Confidence: 0.75
- Para avisos de seguridad/privacidad en UI prefiere estilo discreto y accesible (aside con aria-label, border sutil, contraste bajo) que no compita con el CTA principal de la página. Confidence: 0.75
- Ante trade-offs entre seguridad y conveniencia en CSP/auth/secrets, elige la opción robusta que elimina la superficie de ataque (ej: quitar JSON-LD) sobre la pragmática que la deja expuesta (ej: agregar hash a CSP o permitir 'unsafe-inline') — prefiere perder una feature secundaria antes que debilitar una directiva de seguridad. Confidence: 0.85
- Cuando se enfrenta a un bug de producción en una feature deployada, reporta el error completo del navegador (incluyendo el hash/URL de la directiva violada) junto con su observación del estado funcional ("parece que el reviewer funciona bien"), para que el asistente tenga todo el contexto sin tener que repreguntar. Confidence: 0.8
- Nunca hacer push (a Netlify, GitHub, o cualquier remote) sin su confirmación explícita — esto incluye `git push`, `git push --force`, y `git push --force-with-lease`. Confidence: 0.95
- Nunca hacer operaciones destructivas de reescritura de historial (`git filter-branch`, `git rebase` que cambia SHAs pusheados, etc.) sin su confirmación explícita previa, y aunque la pida, reconfirmar antes del push final. Confidence: 0.95
- Cuando el sistema del asistente agrega metadata automática a los commits (ej: trailers `Co-authored-by:`, firmas, etc.), quiere ser informado explícitamente de qué se está agregando, qué hace, y tener la opción de desactivarlo para commits futuros. Confidence: 0.9
- Prefiere que el asistente desactive trailers/firmas automáticas generadas por el sistema en sus commits, y si es posible, reescriba el historial existente para removerlos — pero entiende que la reescritura tiene costos (force-push, pérdida de referencias por SHA) y acepta el tradeoff cuando se lo explican claramente. Confidence: 0.85
- Cuando una operación riesgosa tiene consecuencias irreversibles (force-push, filter-branch, rebase destructivo), el asistente debe pedir confirmación final ANTES de ejecutar el comando, no asumir que un OK previo general alcanza. Confidence: 0.9
